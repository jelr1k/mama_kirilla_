## Приоритет 1: закрытие приложения через LLM не требует подтверждения

**Где:** `tools/registry.py`, инструмент `close_application`; проверка флага находится в `tools/executor.py`.

В реестре инструмента указано `requires_confirmation: False`. `ToolExecutor` запрашивает подтверждение только для инструментов с включённым флагом. Поэтому путь Tool Calling через LLM может закрыть приложение без подтверждения, в то время как Command Router использует отдельный путь обработки подтверждения.

**Риск:** разные способы вызвать одно действие имеют разные правила подтверждения. Это особенно важно для закрытия приложения с несохранёнными данными.

**Направление исправления:** унифицировать политику подтверждения для Router и LLM-пути, затем покрыть оба сценария тестами. Простая смена флага допустима только после проверки, не появится ли двойное подтверждение или другая регрессия в Router.

**Статус:** подтверждено статическим чтением; исправление не выполнялось.

## Приоритет 1: ожидание подтверждения может остаться заблокированным

**Где:** `services/chat_service.py`, метод `_confirm_tool()` и `shutdown()`.

`_confirm_tool()` ждёт через `event.wait()` без таймаута. В `shutdown()` список ожидающих сообщений очищается и `_pending_confirmation` сбрасывается, но ожидающее событие явно не освобождается.

**Риск:** при закрытии приложения или потере обработчика подтверждения поток, ожидающий решения пользователя, может зависнуть.

**Направление исправления:** предусмотреть явную отмену ожидающего подтверждения при завершении приложения, гарантированное пробуждение ожидающего потока и обработку отмены как результата. Таймаут сам по себе не заменяет корректный жизненный цикл отмены. Добавить тесты на подтверждение, отказ и shutdown во время ожидания.

**Статус:** подтверждено статическим чтением; сценарий не воспроизводился запуском приложения, исправление не выполнялось.

## Приоритет 2: общее изменяемое состояние выбора приложения

**Где:** `tools/applications.py`, `_PENDING_LAUNCH_CHOICES`.

Список кандидатов хранится на уровне модуля и меняется функциями выбора приложения. Это создаёт потенциальный риск смешивания состояний двух последовательных или конкурентных запросов.

**Важно:** само наличие глобального списка не доказывает воспроизводимую гонку в текущем интерфейсе. Не менять эту часть только на основании замечания статического аудита. Сначала определить допустимость параллельных запросов и добавить воспроизводящий тест либо подтвердить реальный пользовательский сценарий.

## Документация: состояние wake word и TTS

В исходниках присутствуют:
- Vosk-детектор ключевой фразы в `voice/wake_word.py`, подключённый к жизненному циклу приложения и интерфейсу;
- локальный Piper TTS в `voice/tts/service.py`, подключённый в `core/application.py`.

При этом в документации было несколько противоречий: README помечал TTS как нереализованный, статус реализации не отмечал wake word, а дорожная карта перечисляла готовые базовые функции как будущие. Эти расхождения исправляются вместе с этой записью.

Не смешивать уже работающий wake word/TTS с ещё не реализованным потоковым TTS, который начинает озвучивание до завершения полной генерации ответа.

## Обязательные ограничения для будущих ИИ-изменений

### Система логирования является осознанным решением

Перед любыми предложениями по логам прочитать [LOGGING_SYSTEM.md](../02_ARCHITECTURE/LOGGING_SYSTEM.md).

Текущая политика намеренная:
- логи описывают текущий запуск;
- bootstrap очищает старые `*.log*` перед новой сессией;
- после закрытия Jarvis текущие логи остаются доступны для диагностики;
- подсистемы имеют отдельные журналы, а ошибки дополнительно собираются в общий `errors.log`.

**Не менять политику очистки, структуру журналов или архитектуру логирования только ради предпочтений ИИ.** Возвращаться к этому решению можно при явном запросе пользователя или при конкретной воспроизводимой проблеме. Тогда до изменения нужно описать проблему, последствия и план тестирования, а также синхронизировать документацию и тесты.

### Большие файлы не являются самостоятельным багом

Размеры `services/command_router.py`, `services/rofl_service.py`, `ui/settings_page.py` и других модулей не требуют немедленного дробления. Не начинать рефакторинг только потому, что файл большой или существует альтернативный архитектурный стиль. Делать его при конкретной задаче, доказуемой причине или согласованном плане, сохраняя поведение и проверяя регрессии.

### Правила Antigravity

В выводе исходного аудита предлагался `.gemini/rules.md`. Не использовать этот путь как будто он гарантированно поддерживается. Текущая документация Antigravity указывает корневые `AGENTS.md`/`GEMINI.md` и `.agents/rules/*.md`; файлы в `.agents/rules/` требуют корректного YAML-заголовка `trigger`. Для базовых правил проекта используется корневой [AGENTS.md](../../AGENTS.md).

Справка: [официальная документация Antigravity Rules](https://www.antigravity.google/docs/rules/).

## Рекомендуемый порядок дальнейшей работы

1. Отдельно исправить и протестировать политику подтверждения `close_application`.
2. Отдельно обеспечить отмену ожидающего подтверждения при shutdown и покрыть жизненный цикл тестами.
3. При необходимости отдельно проверить конкуренцию в `_PENDING_LAUNCH_CHOICES`.
4. После каждого изменения запускать соответствующие тесты, анализировать Git diff и обновлять документы.
5. Не объединять эти задачи с несвязанным рефакторингом.

**Итог:** данный аудит фиксирует два высокоприоритетных риска и один потенциальный риск. Он не является основанием для переписывания существующей архитектуры.
