# Документация Jarvis

Документация проекта собрана в каталоге `docs/`. Корневой `README.md` является обзорным описанием для пользователей.

## Источники истины

- **Правила для агентной работы:** [`AGENTS.md`](AGENTS.md), [`GEMINI.md`](GEMINI.md) и подробный [`02_ARCHITECTURE/AI_WORK_GUIDE.md`](02_ARCHITECTURE/AI_WORK_GUIDE.md).
- **Сквозной индекс кодовой базы и документации:** [`INDEX.md`](INDEX.md) — связь компонентов, исходников и тестов.

1. **Код текущей ветки (`osnova`)** — фактическое поведение.
2. **Тесты** — проверяемое поведение (`pytest`).
3. **[`01_REQUIREMENTS/PROJECT_SPEC.md`](01_REQUIREMENTS/PROJECT_SPEC.md)** — актуальное техническое задание (v3.1).
4. **[`04_STATUS/IMPLEMENTATION_STATUS.md`](04_STATUS/IMPLEMENTATION_STATUS.md)** — что реально реализовано в ветке.
5. **[`01_REQUIREMENTS/ROADMAP.md`](01_REQUIREMENTS/ROADMAP.md)** — что планируется на будущее.
6. Остальные документы — специализированный контекст.

Если код и документация расходятся, код не становится неверным только потому, что Markdown написал обратное. Сначала фиксируем фактическое поведение, затем обновляем документацию.

## Что где искать

### Индексирование кодовой базы
- Полная карта всех подсистем, ссылок на исходные `.py` файлы, классы и тесты представлена в [**`INDEX.md`**](INDEX.md).

### 01 — Requirements
Главные требования и долгосрочное направление. Здесь не должно быть нескольких конкурирующих ТЗ.

### 02 — Architecture
Как устроен проект и какие правила соблюдать при изменении кода. [`AI_WORK_GUIDE.md`](02_ARCHITECTURE/AI_WORK_GUIDE.md) предназначен для ИИ-разработчиков.

### 03 — Features
Подробности отдельных подсистем и пользовательских возможностей (алиасы, команды, интерфейс рабочей области).

### 04 — Status
Только фактическое состояние реализации. Здесь не хранится полноценное ТЗ.

### 05 — Installation
Зависимости и подготовка окружения.

### 07 — Reviews
Исторические ревью и их выводы:
- [`OPUS_AUDIT_2026-10-20.md`](07_REVIEWS/OPUS_AUDIT_2026-10-20.md) — контрольный аудит рисков (подтверждение закрытия приложений и shutdown-зависания исправлены и протестированы).
- [`TECHNICAL_AUDIT_2026-10-16.md`](07_REVIEWS/TECHNICAL_AUDIT_2026-10-16.md) — обзор архитектуры и рисков.
- [`CODE_REVIEW_2026-09-19.md`](07_REVIEWS/CODE_REVIEW_2026-09-19.md) — ранний разбор.

Решённые баги удаляются из рабочей документации или отражаются как закрытые в статусе реализации и ревью.

## Правило для новых документов

Перед созданием нового Markdown-файла нужно проверить, не относится ли информация к существующему документу. Один факт должен иметь одно основное место хранения.

Не создавать отдельный файл только ради списка из нескольких пунктов, если эти пункты относятся к существующей подсистеме.
