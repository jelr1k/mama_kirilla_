# План интеграции `experimental` и `satichik-dev` для Mama Kirilla

**Назначение документа:** пошаговая инструкция для AI-агента, выполняющего локальную интеграцию двух веток репозитория `jelr1k/mama_kirilla_`.

**Целевая ветка интеграции:** `integration/tauri-v2`  
**Базовая ветка:** `experimental`  
**Ветка с изменениями друга:** `satichik-dev`  
**Целевая архитектура интерфейса:** Tauri v2 + React/Vite; Python остаётся ядром приложения. Старый PySide-интерфейс хранится отдельно и не должен случайно возвращаться в основной путь запуска.

---

## 0. Главная задача

Объединить изменения из `experimental` и `satichik-dev` в одной временной ветке так, чтобы:

1. Сохранить весь работающий функционал `experimental`, включая миграцию интерфейса на Tauri v2, React/Vite, HTTP API и WebSocket-шлюз.
2. Включить изменения `satichik-dev`, в частности менеджер игр Steam, систему пользовательских протоколов и профилей, расширение маршрутизатора команд, изменения установщика/запуска, новые тесты и вспомогательные компоненты.
3. Не вернуть старый PySide-интерфейс в каталог основного интерфейса `ui/` и не восстановить Electron как альтернативный основной интерфейс.
4. Не потерять исправления и новые тесты ни одной из веток.
5. Разрешать конфликты осмысленно, опираясь на текущую архитектуру и вызывающий код, а не выбирать целиком «нашу» или «их» версию файла.
6. Проверить не только импорт модулей и прохождение тестов, но и связность полного пути: запуск приложения → запуск Python-ядра → соединение Tauri с API/WebSocket → выполнение команды → отображение результата.
7. Подготовить проверенный результат для дальнейшего Pull Request. Не вносить его в `experimental` автоматически.

**Ожидаемый итог:** отдельная интеграционная ветка с сохранённой историей Git, подключёнными функциями обеих сторон, пройденными проверками и отчётом о том, что проверено, что исправлено и какие ограничения остались.

## 1. Жёсткие ограничения и правила работы агента

### 1.1. Какие ветки можно менять

- Работай исключительно в созданной пользователем на GitHub ветке `integration/tauri-v2`. Если удалённая ветка существует, а локального tracking-ответвления ещё нет, разрешено создать только локальное отслеживающее ответвление от точного `origin/integration/tauri-v2` командой `git switch --track -c integration/tauri-v2 origin/integration/tauri-v2`. Это не создаёт ветку на GitHub. Не создавай и не пушь новые удалённые ветки.
- Перед любыми изменениями проверь, что текущая ветка именно `integration/tauri-v2`.
- `experimental`, `satichik-dev` и `main` являются исходными ветками. Не переключайся на них для внесения изменений и не коммить в них.
- Пользователь самостоятельно создаёт ветки на GitHub и сохраняет локальные резервные копии обеих исходных версий. **Не создавай и не перезаписывай резервные копии вместо пользователя.** До начала работы проверь, что ожидаемая интеграционная ветка доступна локально и на `origin`. Если её нет, остановись и сообщи о блокере. Не создавай новую ветку самовольно.
- Не выполняй `git push`, не создавай Pull Request, не сливай ветку в `experimental` и не меняй настройки GitHub. Для этого потребуется отдельное указание пользователя.
- Не используй `git reset --hard`, `git clean -fd`, принудительный push, удаление веток или другие разрушающие команды.
- Не стирай незакоммиченные изменения пользователя. Если рабочее дерево не чистое, остановись до выяснения, какие изменения принадлежат пользователю. Не используй `stash` автоматически без явного понимания содержимого.

### 1.2. Как обращаться с конфликтами

- Запрещено разрешать весь набор конфликтов одной командой или массовым выбором `--ours` / `--theirs`.
- Не заменяй большие файлы целиком лишь потому, что версия одной ветки кажется новее.
- До ручного разрешения каждого конфликта изучи версии файла в обеих ветках, общую базовую версию, вызывающий код и относящиеся тесты.
- Сохраняй совместимые изменения обеих веток. Если две реализации конфликтуют архитектурно, выбери решение, соответствующее Tauri v2 + React/Vite + Python backend, и объясни это в итоговом отчёте.
- Если невозможно определить правильное поведение без продуктового решения пользователя, не угадывай и не удаляй функциональность. Зафиксируй точный блокер и предложи варианты.

### 1.3. Обращение с инструкциями в репозитории

- Прочитай `AGENTS.md` и релевантные документы проекта до редактирования.
- В `satichik-dev` есть `AGENTS.md`, где рабочей веткой по умолчанию названа `satichik-dev` и запрещено слияние без прямого запроса. Это правило по умолчанию для обычных задач. Текущая задача пользователя прямо разрешает интеграцию, поэтому работай в пользовательской `integration/tauri-v2`; не переключайся обратно в `satichik-dev` и не удаляй/не переписывай `AGENTS.md` только ради обхода этого правила.
- Инструкции репозитория не дают разрешения игнорировать приведённые выше запреты на пуш и изменение исходных веток.

### 1.4. Ограничение объёма изменений

- Не выполняй несвязанный рефакторинг, массовое переименование, обновление всех зависимостей или косметическое переписывание документации.
- Не меняй версию приложения, release-процесс или историю коммитов без необходимости для интеграции.
- Не удаляй старые файлы только потому, что они кажутся неиспользуемыми. Проверяй ссылки, импорты, тесты, сборку и назначение файла.
- Не добавляй произвольное выполнение CMD, PowerShell или shell, не ослабляй песочницу файловых операций и не расширяй сетевой доступ шлюза на LAN.
- Если для теста требуется установка зависимостей, сначала проверь манифесты и скрипты. Не запускай неизвестный установочный `.bat` вслепую и не устанавливай Python/Node/Rust-пакеты глобально, если можно использовать проектное окружение.

## 4. Этап 0. Инвентаризация и проверка рабочей среды

### 4.1. Проверить ветку и рабочее дерево

Выполнить из корня репозитория:

```bash
git status --short
git branch --show-current
git branch -avv
git log --oneline --decorate -12
```

Ожидаемое поведение:

1. Текущая ветка должна быть `integration/tauri-v2`.
2. Рабочее дерево должно быть чистым.
3. Если есть незакоммиченные изменения, не менять их и не продолжать слияние, пока не установлено, кому они принадлежат.
4. Убедиться, что `origin/experimental`, `origin/satichik-dev` и `origin/integration/tauri-v2` существуют и доступны.
5. Убедиться, что пользовательская интеграционная ветка действительно создана от актуальной `experimental`. Если удалённая ветка существует, но локальной ветки ещё нет, создай только локальную tracking-ветку командой из раздела 1.1. Если самой удалённой ветки нет или её база не `experimental`, остановись и сообщи о проблеме. Не пересоздавай удалённую ветку самостоятельно.

### 4.2. Обновить только ссылки на удалённые ветки

```bash
git fetch origin
git status --short
```

`git fetch` обновляет локальные ссылки на удалённые коммиты, но не должен менять файлы рабочей папки.

Проверь фактические вершины:

```bash
git log -1 --format="%H %s" origin/experimental
git log -1 --format="%H %s" origin/satichik-dev
git log -1 --format="%H %s" origin/integration/tauri-v2
```

Если исходные ветки продвинулись после подготовки этого плана, зафиксируй новые SHA и продолжай только после повторного сравнения.

### 4.3. Проверить базу интеграционной ветки

```bash
git merge-base origin/experimental origin/satichik-dev
git merge-base HEAD origin/experimental
git rev-list --left-right --count origin/experimental...origin/satichik-dev
git diff --stat origin/experimental...origin/satichik-dev
git diff --name-status origin/experimental...origin/satichik-dev
```

Убедись, что база текущей интеграционной ветки соответствует актуальной `origin/experimental`. Важно: `git diff A...B` показывает изменения `B` относительно общей точки слияния, а не обязательно окончательный diff между текущими файлами. Используй его для инвентаризации; итоговое состояние проверяй после merge.

### 4.4. Прочитать базовые документы

Перед редактированием прочитать:

- `README.md`;
- `AGENTS.md`, если файл существует в интеграционной ветке;
- `docs/AI_GUIDE.md`, `docs/ARCHITECTURE.md`, `docs/SPEC_AND_STATUS.md` или соответствующие актуальные документы;
- `docs/CODE_REVIEW_TAURI_V2_2026-10-27.md`;
- новые или обновлённые тесты из обеих веток;
- `core/application.py`, `services/chat_service.py`, `services/command_router.py`, `services/gateway_service.py`;
- `ui/src/App.jsx`, `ui/src/services/api.js`, `ui/src/services/assistantSocket.js`, `ui/package.json`, `ui/src-tauri/tauri.conf.json`;
- `core/protocols_manager.py`, `core/steam_manager.py`, `services/stark_protocols.py` из `satichik-dev`.

Не полагайся только на README или отчёт ревью: проверяй актуальный код на соответствующих SHA.

## 5. Этап 1. Снять baseline до слияния

Цель — понять, какие тесты и сборки работали ещё до merge, чтобы не приписывать интеграции старые ошибки.

### 5.1. Проверка тестов двух исходных веток

Предпочтительно проверить обе ветки в отдельных временных `git worktree`, чтобы не переключать рабочую интеграционную папку. Это локальные временные каталоги, не новые ветки GitHub.

Пример для Git Bash/терминала, из репозитория:

```bash

git worktree add --detach ../mama-baseline-satichik origin/satichik-dev
```

В каждом каталоге выполнить `python --version` и, если зависимости уже доступны, `python -m pytest -q`. Не копируй виртуальное окружение вручную без проверки привязанных абсолютных путей. Если необходимого окружения нет, сначала проверь `config/requirements.txt` и используй отдельное виртуальное окружение для worktree, не меняя глобальный Python.

Для фронтенда в `experimental` проверить имеющийся статус сборки и доступность npm. Не запускай установочные скрипты до изучения их содержимого. Если установка зависимостей занимает слишком много места/времени или нужные инструменты отсутствуют, запиши точное ограничение, а не придумывай успешный результат.

После проверок временные worktree можно удалить только если агент сам создал эти каталоги и убедился, что там не лежат пользовательские данные:

```bash

```

Не удаляй каталоги, которые не были созданы в рамках этого этапа. Не запускай `git worktree prune` без необходимости.

## 6. Этап 2. Выполнить слияние без немедленного коммита

Убедись, что текущая ветка — `integration/tauri-v2`, а дерево чистое. Затем:

```bash
git merge --no-commit --no-ff origin/satichik-dev
```

Не создавай merge-коммит сразу. Git может объединить часть файлов автоматически; это не означает, что их логика корректна.

Сразу после операции:

```bash
git status
git diff --name-only --diff-filter=U
git diff --check
```

- `git diff --name-only --diff-filter=U` показывает файлы с неразрешёнными конфликтами.
- `git diff --check` обнаруживает пробелы и маркеры некоторых проблем оформления, но не доказывает корректность логики.

Если Git сообщает о конфликте, разрешай его по одному, пользуясь разделом 7. Если слияние стало неуправляемым, не делай reset. Допустимая команда отмены текущей незавершённой операции — `git merge --abort`; перед её запуском убедись, что нет незакоммиченных пользовательских изменений, которые могли попасть в рабочую папку во время операции.

**Не редактируй `experimental` или `satichik-dev` напрямую.** Все исправления должны происходить только в `integration/tauri-v2`.

## 7. Этап 3. Разрешить конфликты по архитектуре и функциональности

### 7.1. `core/application.py` — обязательное объединение зависимостей

Цель — сохранить оба набора зависимостей.

В финальном файле должны корректно создаваться и связываться, где это требуется:

- `EventBus` и `TaskRunner`;

- `ProtocolsManager`;
- `SteamManager`;
- `GatewayService` для Tauri UI;
- правильный жизненный цикл `start()` и `shutdown()`.

Проверки:

- [ ] Менеджеры создаются один раз на жизненный цикл приложения, если архитектура не требует обратного.
- [ ] `ChatService` получает `protocols_manager` и `steam_manager` вместе с прежними зависимостями.

- [ ] Сохраняются обработчики события, shutdown, обновлений и voice lifecycle.
- [ ] Нет циклических импортов и скрытого создания второго `SteamManager`/`ProtocolsManager` при обычном запросе.
- [ ] Конструктор приложения тестируется через mocks/fakes так, чтобы тест не запускал реальный Ollama, микрофон, системный трей или процесс обновления.

### 7.2. `services/chat_service.py`

Ветка друга расширяет сигнатуру конструктора и маршрутизатор менеджерами Steam и протоколов. Ветка Tauri добавляет или меняет связь сервиса с WebSocket/Gateway через EventBus.

Сохрани обе части:

- поток событий для Tauri;
- события `chat.chunk`, финальный ответ, завершение генерации, ошибки и статусы;
- постановку сообщений в очередь и ожидающие подтверждения;
- `protocols_manager` и `steam_manager`;
- все существующие зависимости и параметры;
- голосовую озвучку ответа, если она была предусмотрена в исходном поведении.

Особенно проверь `refresh_tools()`. После пересоздания `CommandRouter` в нём должны повторно передаваться все необходимые зависимости. Недопустима ситуация, когда Steam/протоколы работают после запуска, но перестают работать после обновления инструментов/настроек. Проверь также, не теряется ли `website_manager` и другие зависимости, которые уже нужны старому маршрутизатору.

Тесты:

- отправка команды Steam;
- команда пользовательского протокола;
- обычная существующая команда;
- неизвестная команда, требующая LLM;
- прямой ответ маршрутизатора;
- потоковый ответ LLM с сохранением полного текста после события завершения;
- ошибка генерации и повторная команда после ошибки;
- пересоздание роутера через `refresh_tools()`.

### 7.3. `services/command_router.py`

Нужно совместить текущую маршрутизацию с новыми маршрутами Steam и протоколов, не ломая существующие команды.

Проверь:

- [ ] Конструктор принимает все нужные зависимости с совместимыми значениями по умолчанию, чтобы старые тесты и места создания не ломались без необходимости.
- [ ] Команды обрабатываются в правильном порядке: однозначные детерминированные команды и протоколы не должны случайно уходить в LLM.
- [ ] Разбор естественных названий игр, английских/русских вариантов и алиасов работает по поведению `SteamManager`.
- [ ] Когда игра не найдена, маршрутизатор не утверждает, что она запущена или установлена.
- [ ] Менеджер Steam не запускает игру по небезопасному непроверенному AppID или произвольному shell-вызову.
- [ ] Пользовательские протоколы ищутся в активном профиле; смена профиля влияет на распознавание.
- [ ] Встроенные команды протоколов сохраняют совместимость, если они предусмотрены старым кодом.
- [ ] Сохраняются команды файлов, мультимедиа, системной телеметрии, Ollama, приложениям, алиасам и workspace.
- [ ] Подтверждение опасных операций по-прежнему проходит через существующую систему подтверждений/разрешений там, где она предусмотрена.
- [ ] Результат маршрутизатора корректно попадает в EventBus и затем в Tauri UI.

Не дублируй весь набор команд в React. Маршрутизация и выполнение команд остаются в Python-ядре; UI передаёт запрос и показывает событие/результат.

### 7.4. `core/config_manager.py` и `config/settings.json`

Не теряй исправление глубокого объединения вложенных настроек в `experimental`.

Проверь:

- [ ] Существующие пользовательские настройки не затираются значениями по умолчанию при обычном запуске.
- [ ] Новое поле `app_title` и связанные настройки Tauri корректно имеют значения по умолчанию, если они нужны текущей архитектуре.
- [ ] JSON остаётся валидным; пользовательские данные/секреты не попадают в Git.
- [ ] Есть регрессионные тесты на вложенные ключи и повторное чтение конфига.

Не смешивай в одном коммите случайные версии модели или несвязанные пользовательские настройки. Не изменяй `model`, заголовок, wake word и прочие пользовательские значения просто ради выравнивания файлов.

### 7.5. `core/dependency_manager.py`, `config/requirements.txt`, запуск установки

Учитывай одновременно Python backend и стек Tauri.

- Сохрани Python-зависимости, необходимые текущим функциям и голосу.
- Не удаляй зависимости только потому, что PySide MainWindow архивирован: headless-код, системный трей или voice могут всё ещё использовать отдельные пакеты.
- Проверь реальные импорты и точки старта перед удалением любой зависимости.
- Установка frontend-зависимостей должна идти через `ui/package.json` и соответствующий lock-файл (`npm ci`), а не через произвольный `npm install` с неконтролируемым обновлением lock-файла.
- Не возвращай Electron dependency/scripts в `ui/package.json`.
- Изменения `start/install_dependencies.bat` должны быть согласованы с `start.bat` и `start/bootstrap.py`; избегай двух разных путей установки, которые устанавливают несовместимые наборы пакетов.
- Не запускай тяжёлые загрузки моделей как часть проверки merge без необходимости.

### 7.6. `start/main.py`, `start/bootstrap.py`, `start.bat`, `start/install_dependencies.bat`

Главный путь запуска должен быть однозначным.

- [ ] Обычный запуск в текущей целевой архитектуре открывает Tauri/React UI, а не `ui_archive.main_window`.
- [ ] Запуск headless Python backend создаёт ядро и Gateway, не создавая одновременно старый главный экран PySide.
- [ ] Режим намеренного запуска legacy UI, если он сохранён для обслуживания, должен быть явным и не активироваться по умолчанию.
- [ ] `start.bat` запускает backend до Tauri и имеет проверку доступности `/health` или другого health endpoint. Фиксированная пауза `ping` — не достаточная проверка готовности сервиса.
- [ ] При неудачном запуске фронтенда не остаётся бесконечно работающий orphan backend.
- [ ] Закрытие Tauri и завершение backend имеют чёткий, воспроизводимый сценарий.
- [ ] Не запускаются два экземпляра gateway на одном порту.
- [ ] Запуск не требует установленного Electron.
- [ ] Разработческий запуск (`tauri dev`) и сборка приложения (`tauri build`) не смешаны в один неясный путь.

**Критический пункт:** текущий `start.bat` из `experimental` пытается принудительно завершать PID, слушающий порт `8765`. Не оставляй автоматическое завершение любого процесса на этом порту без проверки, что это действительно оставшийся экземпляр Mama Kirilla. Если порт занят посторонним процессом, безопаснее вывести диагностическое сообщение и остановить запуск, чем завершить чужой процесс.

Проверь завершение приложения:

- остановка gateway прекращает поток телеметрии;
- отключение WebSocket не должно приводить к случайному `os._exit(0)` внутри pytest или уничтожать посторонний процесс;
- если автозавершение backend при отсутствии UI требуется, оно должно иметь ясную политику и тестируемый жизненный цикл;
- ошибка при запуске Tauri должна приводить к контролируемой остановке собственного backend.

### 7.7. `services/gateway_service.py`

Gateway — граница между React/Tauri и Python. Его нельзя рассматривать как второстепенную обвязку.

Обязательно проверить:

- [ ] Все существующие endpoints текущего UI сохранены.
- [ ] События EventBus доставляются к нужным WebSocket-клиентам.
- [ ] Полный ответ LLM остаётся в истории после окончания стриминга; временный chunk не должен исчезать без финального сообщения.
- [ ] Ошибки API возвращаются в понятном и проверяемом формате.
- [ ] Остановка приложения не используется в unit-тестах реальным `os._exit`.
- [ ] Gateway слушает loopback `127.0.0.1`, если локальный доступ — ожидаемая модель; не менять адрес на `0.0.0.0`.
- [ ] CORS не расширяется до произвольного сайта и не ослабляется до `*`.
- [ ] WebSocket-подключение проверяет ожидаемый Origin для Tauri и Vite dev, либо риск и допустимые источники документированы и протестированы.
- [ ] Внешний запрос не может произвольно исполнить shell-команду или обойти разрешения ToolExecutor.
- [ ] Конфигурация и команды проходят валидацию на серверной стороне.

Не удаляй endpoints ради устранения ошибки фронтенда. Сначала проверь контракт UI и исправь base URL/маршрут соответствующим образом.

### 7.8. Steam: `core/steam_manager.py`

Steam-функциональность должна быть рабочей независимо от старого интерфейса.

Проверь следующие сценарии через моки/фикстуры, а затем безопасно на реальной среде:

- поиск корневой папки Steam через реестр и поддерживаемые fallback-пути;
- чтение `libraryfolders.vdf` и поиск библиотек на дополнительных дисках;
- перечисление только реально установленных игр, а не всех записей каталога;
- исключение служебных AppID и redistributables;
- распознавание Steam AppID и распространённых русских/английских псевдонимов;
- обработка неизвестной игры и неоднозначного совпадения;
- проверка, запущена ли игра;
- запуск через валидированный `steam://rungameid/<appid>` без произвольного shell;
- кеширование сканирования и обновление кеша по TTL;
- graceful behavior, если Steam не установлен, реестр недоступен, библиотека повреждена или процесс недоступен.

Проверяй использование `winreg` в тестах: модули должны быть мокированы, чтобы тест не запускал реальный Steam и не требовал установленной библиотеки. Не добавляй жёстко зашитые пути пользователя как единственный способ работы.

### 7.9. Пользовательские протоколы: менеджер и исполнитель

Объедини `core/protocols_manager.py` и `services/stark_protocols.py` с текущей архитектурой.

Проверить:

- создание профилей и переключение активного профиля;
- список, сохранение, обновление и удаление пользовательского протокола;
- корректность ID и защиту от дубликатов;
- чтение настроек из пользовательского файла и восстановление defaults при отсутствии файла;
- поиск фраз с нормализацией пробелов/регистра и вариантами «протокол»/«режим»/«джарвис»;
- выполнение каждого поддерживаемого типа действия;
- правильную обработку ошибки одной операции, чтобы не сообщать, что весь протокол выполнен, если действие не удалось;
- отсутствие исполнения произвольного кода из JSON-конфига;
- корректную связь ответа протокола с чатом и озвучиванием.

**Опасные действия:** протоколы могут закрывать процессы, блокировать Windows и очищать корзину. Перед подключением в новую UI/API границу проверь, как уже устроены разрешения и подтверждения. Не обходи их ради удобства. Операции с уничтожением данных, закрытием неизвестных процессов или блокировкой экрана должны быть явно обозначены пользователю и безопасно подтверждаться согласно политике проекта.

### 7.10. Портирование страницы протоколов в React/Tauri

## 8. Этап 4. Проверить HTTP API, WebSocket и React

### 8.1. Централизованный API-клиент

Проверь `ui/src/services/api.js` и найди все прямые сетевые вызовы в `ui/src/`:

```bash
git grep -n "fetch(" -- ui/src
```

Вызовы REST API должны использовать общий API-клиент или централизованную функцию URL, чтобы в Tauri запросы шли на `http://127.0.0.1:8765`, а в Vite dev корректно работал proxy. Не допускай разрозненных адресов по компонентам.

В текущем `ui/src/App.jsx` уже встречается прямой вызов `fetch('/api/shutdown')`. Проверь и исправь этот путь, если он по-прежнему присутствует в интегрированной версии: в Tauri такой относительный URL может указывать на origin frontend, а не на Python gateway.

Проверь:

- загрузку и сохранение настроек;
- статус/телеметрию;
- список команд;
- чат;
- алиасы;
- Ollama и инструменты;
- workspace;
- веб-сайты, если они поддерживаются UI;
- профили и протоколы;

### 8.2. WebSocket и потоковый чат

Проверь `ui/src/services/assistantSocket.js`, `ui/src/services/useAssistant.jsx`, `ui/src/components/Chat.jsx` и события в `GatewayService`/`ChatService`.

Требуемое поведение:

1. Пользователь отправляет текст.
2. Backend получает запрос и отображает статус обработки.
3. При генерации отображаются chunks.
4. После `generation_finished` итоговый ответ становится постоянным сообщением истории.
5. Временный chunk-индикатор исчезает, но текст ответа не исчезает.
6. Прямой ответ `CommandRouter` добавляется ровно один раз.
7. Ошибки, очередь запросов и отмена не приводят к дубликатам или потере истории.
8. При обрыве WebSocket UI показывает соединение/ошибку и пытается восстановить связь без создания дублированных сообщений.

Пиши регрессионные тесты на события, а не только на существование компонентов.

### 8.3. Согласованность API-контрактов

Для каждого React-компонента, который вызывает API, сопоставь:

- HTTP-метод;
- URL;
- ожидаемый JSON-запрос;
- ожидаемый JSON-ответ;
- поведение при HTTP-ошибке;
- реализацию endpoint в `GatewayService`;
- тест контракта.

Нельзя считать функцию интегрированной только потому, что фронтенд-компонент отображается или endpoint отдаёт HTTP 200 с пустым объектом.

### 9.3. Обязательные новые проверки, если их нет

Добавь минимальные тесты для следующих сценариев:

**Application/wiring**

- `ProtocolsManager` и `SteamManager` создаются и передаются в `ChatService`.
- `GatewayService` получает то же приложение и не создаёт вторую копию managers.
- `refresh_tools()` сохраняет все зависимости маршрутизатора.

**Command Router**

- Известная установленная Steam-игра разрешается по названию/алиасу и запускается через mock.
- Неизвестная игра не приводит к попытке запуска произвольного файла.
- Команда пользовательского протокола выполняет ожидаемый исполнитель.
- Обычные команды из существующего набора сохраняют поведение.

**Protocol Manager**

- Добавление/изменение/удаление протокола.
- Создание, переключение и удаление профиля с соблюдением правил для default-профиля.
- Поиск фразы в активном профиле.
- Повреждённый JSON и отсутствие файла обрабатываются контролируемо.

**Settings**

- Частичное изменение одного вложенного поля сохраняет соседние ключи.
- После сохранения данные корректно читаются повторно.

**Gateway/API**

- API-путь профилей/протоколов возвращает ожидаемую схему.
- Неверный payload получает ошибку, а не вызывает исключение, убивающее сервер.
- Запрос на чтение не имеет побочных эффектов.
- CORS и WebSocket Origin проверяются по ожидаемому allowlist.
- Тест shutdown не вызывает реальное завершение процесса тестов.

**Streaming**

- Чанк-ответ превращается в постоянное сообщение после генерации.
- Прямой ответ маршрутизатора не дублируется.
- Ошибка генерации не оставляет UI в вечном состоянии `thinking`.

**Tauri UI**

- Smoke test проверяет наличие React/Tauri-конфигурации без Electron.
- Профили и протоколы можно загрузить и сохранить через UI/API.
- В UI корректно отображаются ошибки API и отключённый backend.

Тесты не должны реально закрывать процессы пользователя, очищать его корзину, блокировать рабочую станцию, включать микрофон, запускать Ollama или делать сетевые запросы к внешним сервисам без mock/явного отдельного ручного теста.

### 9.4. Полный набор

После исправления всех тестов:

```bash
python -m pytest -q
```

Если полный набор не проходит:

1. Сохрани полный лог, а не только последнюю строку.
2. Раздели ошибки, присутствовавшие в baseline, и новые ошибки интеграции.
3. Исправь регрессии, вызванные объединением.
4. Если проблема была и до объединения, не маскируй её и не приписывай успех тестам; отметь её отдельно.
5. После каждого исправления, затрагивающего общий модуль, повтори соответствующие выборочные тесты и затем полный набор.

Не ставь `xfail`, не удаляй assertions и не ослабляй тестовые проверки просто для получения зелёного прогона. Любое сознательное изменение ожидаемого поведения должно иметь обоснование и тест нового контракта.

## 10. Этап 6. Проверки React, Tauri и сборки

5. Не коммить бинарные артефакты сборки без проверки существующей политики проекта. Не удаляй уже отслеживаемые bundle-файлы автоматическим чистильщиком.

### 10.1. Ручной запуск dev-режима

Если требуемое окружение доступно, выполни dev-режим и проверь полный жизненный цикл:

- backend действительно стартовал;

## 13. Этап 9. Итоговый diff и контроль целостности

После устранения конфликтов и выполнения исправлений проведи ревью полного изменения относительно базовой `experimental`.


Последняя команда должна вывести пустой список. Затем просмотреть diff по группам:

1. ядро и жизненный цикл;

7. тесты;

```bash
git diff --stat origin/satichik-dev...HEAD
git diff --name-status origin/satichik-dev...HEAD
```

Это нужно для анализа, а не для попытки сделать обе ветки файлово идентичными: итоговая ветка сознательно использует Tauri вместо старого PySide UI. Убедись, что отличия от ветки друга объяснены архитектурой, а не случайной потерей функциональности.


Результат должен быть пустым, кроме редких обоснованных случаев, когда такие строки намеренно упомянуты в документации. Проверь их отдельно.

## 14. Этап 10. Финальный коммит в интеграционной ветке

Только когда конфликты разрешены, diff проверен, тесты завершены и сборка проверена (либо её невозможность явно задокументирована), создай локальный merge-коммит.

Перед коммитом:

```bash
git status
git diff --cached --check
git diff --cached --stat
```

Убедись, что в staging нет ничего лишнего. Не используй `git add .` вслепую, если в рабочей папке могут оказаться артефакты сборки, логи или локальные данные. Добавляй файлы осознанно или сначала внимательно изучи `git status --short`.

Если merge начат командой `git merge --no-commit --no-ff`, завершай именно его после проверки:

```bash
git commit
```

Используй понятное сообщение, например `merge: integrate satichik-dev into Tauri v2`. Не squash-коммить всю историю друга и не делай rebase, изменяющий опубликованную историю исходных веток.

**После коммита не выполняй push автоматически.** Остановись на проверенной локальной ветке и подготовь отчёт пользователю.

## 15. Формат обязательного отчёта агента

### A. Git-состояние

- SHA базы merge;
- SHA итогового коммита;

- какие функции Steam подключены;
- какие функции протоколов/профилей подключены;
- как протоколы доступны из Tauri UI;
- какие изменения Tauri/UI и Gateway сохранены;
- какие дополнительные исправления внесены для связности системы.

### C. Конфликты

Перечисли конфликтующие файлы и для каждого кратко объясни, что было взято из обеих веток и почему принято конкретное решение. Не ограничивайся фразой «конфликты решены».

### D. Проверки и результаты

Для каждой команды/проверки укажи фактический результат:

- baseline `experimental`;
- baseline `satichik-dev`;
- полный `python -m pytest -q`;
- выборочные тесты Steam/протоколов/Gateway/UI;
- `npm ci`;
- `npm run build`;
- `npm run tauri:build`;
- ручные проверки запуска и функциональности.

Записывай количество тестов и failed/skipped. Не называй тест пройденным, если его не запускали. Не называй Tauri-сборку успешной, если не было подходящего Rust toolchain.

### E. Оставшиеся проблемы

По каждой проблеме укажи:

- воспроизводится ли она;
- существовала ли на baseline;
- блокирует ли она запуск или функциональность;
- какие файлы затронуты;
- что нужно сделать дальше.

### F. Следующий шаг

Укажи, что ветка готова или не готова к пользовательскому ревью. Не пушь её и не создавай PR: это решение остаётся за пользователем.
